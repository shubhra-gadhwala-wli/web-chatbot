# WLI-9 Discovery research brief — local RAG voice chatbot

**Research date:** 2026-09-25  
**Scope:** registered users upload PDF, `.txt`, `.md`, etc.; converse by text and browser-native Web Speech API; local/non-cloud vector store; end-to-end local use. Sources are linked inline and dated as accessed on 2026-09-25. Evidence grades: **P** = primary/official documentation; **O** = official vendor documentation; **S** = standards/regulator.

## Executive finding

**Recommendation: build the web application and integrate mature local components, rather than buy a document-chat product.** The decisive constraint is not RAG itself: it is the combination of registered-user isolation, a non-cloud vector store, and browser-native speech. The reviewed SaaS products offer document chat but are cloud services; reviewed local products demonstrate that local RAG is viable, but none was verified from its public documentation as providing this exact registered-user web product with real-time browser-native STT/TTS. Browser-native recognition also cannot be promised as fully offline or cross-browser: MDN marks `SpeechRecognition` as limited availability and says some browsers send audio to a server-based recognition engine. **P** [MDN SpeechRecognition](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition).

For a first local deployment, the lowest-complexity fit is **LanceDB embedded locally + a local embedding model + PDF.js for PDFs and native text/Markdown handling**, with an application-owned relational database for accounts, document metadata, and per-user authorization. This is an engineering recommendation from the evidence below, not a claim that the choice is the only viable stack.

### Competitive conclusion and disconfirming evidence

* Local document chat is already feasible: AnythingLLM, PrivateGPT, and Khoj each publicly document local/self-hosted paths. This weakens any claim that a generic “chat with PDFs” product is novel. **O** Sources above.
* The product’s differentiation must therefore be the constrained, privacy-preserving **web** experience and reliable user/document isolation, not merely “RAG”.
* The requested voice constraint is a delivery risk, not a market moat by itself. Web Speech Recognition is neither broadly interoperable nor reliably local; a Chrome-style browser can use server recognition even when the application calls only the native API. **P** [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition). This directly disconfirms any promise of “offline/private STT” based solely on the phrase “browser native.”

### Integration constraints

* **Embedding compatibility:** all candidate stores accept vectors, but a collection/index must use one stable vector dimension and similarity metric. The explicit examples differ: MiniLM is 384-dim, PrivateGPT’s cited `mxbai-embed-large` is 1,024-dim, and OpenAI’s `text-embedding-3-large` can be shortened from 3,072 dimensions. Model changes therefore require versioning and re-indexing. **O/P** [MiniLM](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2), [PrivateGPT](https://docs.privategpt.dev/providers/overview), [OpenAI](https://developers.openai.com/api/docs/guides/embeddings).
* **Browser speech:** use `SpeechSynthesis` and `SpeechRecognition` only, per requirement; feature-detect recognition, provide text fallback, and disclose the browser/provider behavior. On-device recognition is experimental and may require language packs and a Permissions Policy. **P** [MDN usage](https://developer.mozilla.org/en-US/docs/Web/API/Web_Speech_API/Using_the_Web_Speech_API), [availability](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition/available_static).
* **Parser boundary:** accept file allow-lists, size/page/time limits, content-type detection rather than filename trust, and isolate parser workers. Tika itself calls out limits/robustness and security configuration for untrusted content. **P** [Tika docs](https://tika.apache.org/docs/).

## Regulatory and compliance surface (flag, not legal advice)

**Local-only first release:** even if data stays on the user’s machine, uploaded documents and account records may contain personal data. The exact legal role, jurisdiction, categories (including health/payment/children’s data), and whether the operator can access telemetry/backups are not stated, so no legal compliance conclusion is possible.

**If later publicly deployed:**

* For UK/EU-type processing, capture a data inventory and lifecycle: purpose, minimization, retention/deletion, access, and security. The ICO says privacy-by-design/default requires technical and organisational measures throughout the lifecycle and that default use should be limited to what is necessary; it explicitly calls out a retention schedule and deletion of data no longer needed. **S** [ICO guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/guide-to-accountability-and-governance/data-protection-by-design-and-by-default/).
* Per-user isolation is a product requirement with compliance impact: enforce authorization at file, chunk, embedding, retrieval, chat-history, backup, and deletion paths. A local vector store is not automatically private—Qdrant’s own quickstart says its default local configuration has no authentication/encryption. **O** [Qdrant](https://qdrant.tech/documentation/quickstart/).
* A hosted embedding/LLM or speech provider changes the data-flow analysis: document text or audio can leave the local environment. This must be disclosed and contractually evaluated before a public deployment; it cannot be treated as local merely because the vector DB is local.
* CCPA/CPRA scope depends on the future business and data facts. California’s official materials cover consumer notices/requests and rules around service providers/contractors; determine applicability with counsel when a public service and its thresholds are known. **S** [California DOJ regulations](https://oag.ca.gov/privacy/ccpa/regs), [CPPA regulations](https://cppa.ca.gov/regulations/consumer_privacy_act.html).
* Accessibility is relevant to a voice UI: text input/output and controls remain necessary because recognition support is limited. WCAG 2.2 is a W3C Recommendation and provides technology-neutral testable criteria. **S** [WCAG 2.2](https://www.w3.org/TR/wcag/).
* HIPAA, PCI DSS, app-store rules, and sector-specific retention rules are **not assumed applicable**. They become material only if the product is positioned for covered healthcare/payment use, handles card data, or is distributed through a governed mobile-store surface.

## Round-2 decisions and what I could not determine

1. **LLM/embedding data boundary (required):** Is an external API key allowed for chat and/or embeddings, or must all inference be local/offline? This determines hardware, latency, operating cost, data transfer, and model choice. Resolve through CEO intake round 2; do not request credentials yet.
2. **Target browser/OS and offline promise (required):** The Web Speech API requirement does not establish which browsers must work. Recognition is limited-availability and may be server-backed. Resolve supported-browser matrix and whether “browser-native” permits browser-provider network processing.
3. **Scale and hardware:** no users, documents/user, pages, concurrent chats, languages, file-size, latency, or target-machine CPU/RAM/GPU figures were supplied. These are needed for a credible build/hardware cost range and vector benchmark.
4. **Document fidelity:** scanned PDFs/OCR, tables, images, DOCX/PPTX/CSV, and multilingual extraction are not specified. The brief names “etc.” but does not make a format acceptance promise; choose an explicit initial allow-list.
5. **Current commercial details not verified:** NotebookLM’s and ChatPDF’s current first-party price/limit tables, and public confirmation of browser-native live voice for every reviewed competitor, were not found in the reviewed sources. Absence of a cited statement is not proof a feature is absent.
6. **Legal applicability:** operating entity, launch countries, audiences (especially children), data categories, retention terms, and actual cloud telemetry/backup flows are unknown. Legal counsel and a data-flow inventory would resolve this before public launch.

## Handoff

**Decision-relevant finding:** browser-native `SpeechRecognition` is not a dependable proxy for offline/private or universal STT; it needs a text fallback and an explicit browser/privacy policy.  
**Biggest remaining unknown:** whether external LLM/embedding APIs are permitted. It determines both the real local-hardware requirement and the data boundary.
